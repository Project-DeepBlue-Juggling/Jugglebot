# BUG-67: full-length Columns goal ended MISSED_CATCH on its final Catch

**What.** On 2026-11-04 18:45 (goal 3, 48/48, skill 50 of 50) and 2026-10-28 09:49 (skill 35 of 35) a clean full-length goal ended `MISSED_CATCH` because the cup read EMPTY over the final Catch's window. That window closes at landing + 0.50 s; the Stop (Ball 2's carried Throw) lands after it, so the first SEATED read is outside the window and the bag cannot say whether the ball seated. This is the owner's temporary answer (TKT-38, option 4: "book the end as 'ended on a Stop, final Catch unverifiable'"), pending the Tracker rule (option 3, judge by the Tracker), which is not built.

**Change (a label fix, no motion).**
- `executor.py`: `_register_catch` computes `ends_on_stop` once (plain CATCH, no carried Throw, the schedule's last CATCH with only RESTs after it, `schedule_has_shadow_landing`). In `_advance_catch_evidence`, a LIVE window with `n_seated == 0` on such a Catch logs `CATCH-EVIDENCE-UNVERIFIABLE ...`, sets `final_catch_unverifiable = catch_idx`, and sets no `end_code`, no `attempt_ended`, no `lost_ball_line`, no survivor tail. The ball's pending OUTCOME rows are kept and marked `final_unverifiable`; one that then finalises reports `caught=None, unverified=True` whatever the cup reads later (OUTCOME line `caught=unverifiable (...not counted)`; see the 2026-11-07 paragraph), and still writes its learner row (admission is not by the Catch verdict; `Experience.caught` is False). A BLIND, not-LIVE or SEATED window behaves as today; a final Catch of a schedule with no Stop, or a non-final Catch, still ends `MISSED_CATCH` (survivor behaviour unchanged).
- `report.py`: `ThrowReport.unverified` (the smallest new value; neither caught nor missed nor counted, like `stop`); `summarise` and the `end_line` tally exclude it, so the operator's tally of a 48/48 goal stays 48/48 (since 2026-11-07 the ledger counts it too, but only on a COMPLETED goal whose row has a landing, TKT-44 below) and the end line gains ` · ended on a Stop, final Catch unverifiable`; `end_line(final_catch_unverifiable=)`.
- `skill_node.py`: `_log_attempt_end` passes the executor's attribute. `end_code` stays empty, so the Juggle outcome is `COMPLETED` and `records.category` reads `completed`; no interface field added (no colcon rebuild). `INVARIANTS.md` does not state the MISSED_CATCH rule, so nothing to update there.

**Review correction (2026-11-06, same day).** The first version's predicate required the final Catch to be the schedule's LAST SKILL, which never holds on a real compile (`... CATCH carrying the Stop, CATCH, REST`); its hand-built test fixture had no closing REST and hid it, so do not copy that fixture. The predicate is now: plain CATCH, no carried Throw, no CATCH or THROW after it (only RESTs), and `schedule_has_shadow_landing`. Which `compile_*` variants qualify (checked by calling the predicate on real compiles, `/tmp/jb169_variants.py`): `compile_columns` n_throws >= 2 (n = 6, 20, high-low `apex_m_ball_b`, turned `columns_sites(.., angle)`, `feed=`, `hop_entry=True`) fires on the last CATCH only. No Stop, so a miss stays a miss: `compile_columns` n_throws = 1, the one-ball columns (`phantom_balls`, the Stop is the phantom's, so `schedule_has_shadow_landing` is False), hence also `compile_reload_columns` and `compile_rest_columns` (both end in that phantom compile), `compile_one_ball` self-Throw, hop and the fixed-role oval.

**Motion walk, redone with the real REST.** A real columns tail is skill 49 CATCH (carries the Stop), 50 plain CATCH at landing L, 51 REST. The REST's `dispatch_s()` is L + 0.125 s (REST t = L + 0.65 s, window 0.3 s, lead 0.225 s); the verdict fires at L + 0.50 + 0.03 s, 0.40 s later. `tick` runs the dispatch loop before `_advance_catch_evidence`, so the REST is installed before the verdict. On the flown goal 3 of 2026-11-04 18:45 (`~/.ros/log/2026-11-04-18-45-46-408268-jetson-337712/launch.log`): the final CATCH splice, line 2325 (`CATCH skill 50`, t_land 479.527); the REST installed at lines 2350-2351 (`install_segment REST Ball 1`, `REST skill 51: fresh origin`, at 479.616, 0.09 s after landing); the verdict at line 2353 (`END MISSED_CATCH`, 480.068, 0.45 s after the REST). So today's `attempt_ended` came AFTER the REST was already installed and flown: it moved nothing, and the unverifiable end is motion-identical to it, and to a clean full-length goal (2026-11-03 22:29), whose REST path it now takes. After the verdict nothing is left to dispatch, `stop_terminals` has no pending release (`[]`), `_maybe_hold_pending_event` and `_maybe_cancel_bb_throw` are no-ops (the last release was long past). Closing decay: `_plan_closing` (only entered after an END) takes the last accepted install: the REST (`rest_tilt` None, level) or, if the REST were somehow still undispatched, the final CATCH (`hold_tilt` None): not tilted, so no decay is planned either way. If the REST were still undispatched at the verdict (it is not on a real compile), the old end skipped it and this one dispatches it as a clean goal does. The test asserts the REST is in `dispatched` when the UNVERIFIABLE line is logged.

**Owner's answer in TKT-42 (2026-11-07): option 2, plus two fixes.** Three changes, label and bookkeeping only; nothing touches a hold, REST, decay, dispatch or install. (1) A false CAUGHT: `_row_unverified` now reads the `final_unverifiable` flag alone, so a SEATED read after the verdict no longer turns a booked row CAUGHT while the end line says unverifiable. On the flown 2026-11-04 goal the Stop's own seat (480.203) falls inside Ball 1's row window (ends 480.227), so it is not that Catch's evidence; `_finalise_outcome` also sets the Experience's `caught` False for a booked row, so the Stop's seat never writes a Memory row with caught=True (grep of `motion/skills/`: `caught` is read only by the report, the Experience field and the memory CSV; no fit or learner path keys on it). (3) The records count: new `report.record_counts` is `summarise` with every unverified row added to both sides, and `_juggle_execute` passes that to `_offer_record`, so the ledger reads N/N; the Juggle Result, feedback, attempt event and the end line keep `summarise` (N-1/N-1 with "ended on a Stop, final Catch unverifiable"). `records.category` reads the end code only and the comparison takes plain ints, so `records.py` is unchanged. The only other `summarise` callers are the feedback loop and the Result, which stay operator-facing.
