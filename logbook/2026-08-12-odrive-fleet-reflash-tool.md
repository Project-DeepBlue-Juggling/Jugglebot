# Fleet-wide leg-ODrive config reset tool

## What changed

`tools/odrive_fleet_reflash.py` automates, across all six leg drives in one
pass, the procedure this project has run one drive at a time:
`erase_configuration()` in the `odrivetool` shell, then `odrivetool
restore-config`, then re-set `axis0.config.can.node_id` and save. The motivation
is the standing quirk this machine has: its ODrives occasionally need a config
reset (one cured the 2026-08-10 leg-0 `SPINOUT_DETECTED`), and a bare reset
reverts every tuned value — so the reset is only half the job.

Per drive: record USB-serial → node-ID for the whole fleet and write it to
`fleet_map.json` *before* anything is erased → back up the live config (the
format `odrivetool backup-config` writes, so it is restorable by hand) → erase
+ reboot → restore `config/ODrive config Files/odrive_pro_leg_config.json` with
that drive's own node ID already patched in → save → reboot → verify every
property in the file against what NVM now holds. Node 6
(`NODE_ID_JUGGLEBOT_HAND`) is discovered, recorded, and never written to; the
leg/protected sets come from `protocol_config.yaml` via the generated module,
not from a literal in the script. Default run is unattended (owner's choice);
`--dry-run` does discovery + backup + diff and touches nothing.

## Discussion — three choices a future reader would not infer from the code

**The node ID is patched into the restore dict, not fixed up after it.** The
manual flow restores the snapshot — which carries `node_id = 0`, being a leg-0
capture — and then corrects the node ID in a second save. That leaves a window
in which node 0 is committed to NVM, and running six drives through the same
procedure means every one of them is persistently node 0 until its own second
save lands. Patching before the single save closes the window and costs one
fewer reboot.

**The verify pass forces a reboot before it reads.** After the restore the
intended values are already in RAM, so reading a live drive cannot distinguish
a `save_configuration()` that took from one that silently refused — an armed
axis will refuse. Only a post-reboot read is evidence about NVM. The erase step
reboots for the mirror-image reason: it clears RAM as well, so any property the
snapshot does not cover lands on firmware defaults instead of surviving the
"reset" untouched.

**Per-motor calibration is deliberately NOT preserved.** The snapshot carries
`commutation_mapper.config.index_offset = 0.47440463` with
`index_offset_valid: true`, plus measured `motor.phase_resistance` /
`phase_inductance` — physically per-assembly values, since the legs commutate
off INC_ENCODER0 with an index GPIO. Flashing verbatim therefore writes the
snapshot drive's rotor-alignment offset onto all six. Owner's call (2026-08-12):
these are regenerated by the next index search, so verbatim is right and
preserving them per-drive would be the wrong fix. **Consequence: home every leg
before arming it** — the script prints that on exit.

Three places refuse rather than guess, because guessing is expensive in each:
duplicate node IDs abort the run (that is the post-interrupt state, where an
erased drive's default ID collides with leg 0 — `--map` then resolves node IDs
by USB serial instead of by live read); an unrecognised node ID aborts (a
BallButler drive at 7/8 on the USB tree must not receive a Jugglebot leg
config); and a target file whose `commutation_encoder` is not INC_ENCODER0
aborts, since that is the hand snapshot (ONBOARD_ENCODER0) and it would leave a
leg with no wired commutation source. A live `teensy_bridge_node` /
`jugglebot_launch` / `odrivetool` / ODrive GUI also aborts it: the first three
command these node IDs over CAN while they are being reflashed, the last two
hold an exclusive USB claim. `--force` overrides all of them.

## Verification

`./run_tests.sh` (run 2026-08-12): **5077 passed, 0 failed in 223.66 s**; serial
phase empty (5512 deselected, every `serial` test is also `nightly`); total 236 s,
`RESULT: PASS`.

`pytest tests/motion/test_odrive_fleet_reflash.py -q` (run 2026-08-12): **41
passed in 0.20 s**. Covers the pure decision logic — node-ID patching (asserted
to change exactly one property), the NaN-aware verify diff (the snapshot really
does carry NaN, so a naive `==` would report every such property as a failed
write), fleet validation, and the target-file/process preflights — with the real
leg *and* hand snapshots as fixtures, so an edit to either that breaks the
node-ID path or flips the commutation encoder fails here rather than on the
bench.

**Not exercised against hardware.** No ODrives were on USB this session
(`lsusb -d 1209:` empty), so every hardware path — discovery, erase, restore,
reboot-and-refind, verify — is untested. First use should be `--dry-run`: it
records the fleet map, backs up all six drives and prints the per-drive diff
against the target without erasing anything.
