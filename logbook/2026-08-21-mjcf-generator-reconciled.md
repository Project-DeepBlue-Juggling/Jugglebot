# The MJCF model stopped being generated in March and nobody noticed for five months

## Summary

`sim/model/jugglebot.xml` is generated by `sim/model/generate_mjcf.py`. It stopped
being a generated artifact on **2026-03-30** and the two files never rejoined.
Running the generator on 2026-08-21 produced a 38-line diff of which **one line was
a wanted fix and the rest was destruction** — it would have deleted the second ball
outright and cut the ball from 35 mm / 71 g to 20 mm / 43 g.

The generator is now back to being the real source of truth: it reproduces the
committed XML byte-for-byte apart from the intended hand-stroke correction, the ball
spec moved into `config/hardware_config.yaml`, the XML carries a
`GENERATED FILE — DO NOT EDIT` header, and `tests/sim/test_mjcf_drift.py` fails if
the two ever disagree again.

## Motivation

The histories diverge at `1953943` (2026-03-22). The generator's only later commits
before today (`ed624fc`, `c74761b`, both 2026-03-23) were comments, prints and dead
code with **no output change**, so the XML lost nothing from that side. The XML then
took four substantive hand-edit commits — `06136ef` (2026-03-30), `4f94438`
(2026-05-22, two-ball support), `a3c5d5a` (2026-05-23), `5704df5` (2026-05-24).

Measured today, the generator did not emit:

1. **The second ball** — the `ball2` body, freejoint, geom, site, its `ball2_mat`
   material and its `ball2_pos` / `ball2_vel` sensors. Eight references in the XML,
   zero in the generator. `sim/ball/manager.py` discovers balls by scanning
   `ball`, `ball2`, `ball3`, … upward *until one is absent*, so deleting `ball2`
   would have silently dropped the model to one ball rather than failing loudly.
   `tests/sim/test_multiball.py` asserts `ball_manager.ball(1).name == 'ball2'`.
2. **The `<contact><exclude body1="ball" body2="ball2"/>`** and its reasoning.
3. **The real ball spec** — the XML says `size="0.035" mass="0.071"`, the generator
   said `size="0.02" mass="0.043"`.

Four things had to be simultaneously true for this to survive five months, and every
one of them is a general property, not an accident of this file:

- the XML carried **no generated-file header**, so four separate authors edited a
  generated file with nothing in front of them saying it was one;
- it does **not live in a `generated/` directory**;
- the generator asserted nothing beyond a closing `print(f"Generated {out_path}")`;
- **nothing tested that the two agreed.** `tests/sim/test_model.py` loads the XML
  and never mentions `generate_mjcf`.

The identical failure class was already solved once in this repo, for
`config/generated/*`, by `tests/firmware/test_config_drift.py` (see
`logbook/2026-08-01-config-drift-gate.md`). That gate is what this one is modelled on.

## Discussion

### Why bring the generator up to date rather than retire it

The obvious cheaper option was to declare the XML the source of truth and delete
the generator — it had been dead for five months and nothing depended on it. Three
things ruled that out:

- **The XML is derived data.** Six leg quaternions, six leg lengths, twelve node
  anchors and the platform inertia tensor are all computed from
  `config/hardware_config.yaml` by `rotation_from_z_to_dir` and friends. Freezing
  the XML means the next geometry change has to be applied by hand to numbers
  printed at six decimal places, in a file where a wrong quaternion is a silently
  wrong Stewart platform rather than a parse error.
- **The staleness was real and was already biting.** `hand_stroke_mm` moved
  355.0 → 344.75 on 2026-08-18 and the XML still carried `0.355000` on both
  `hand_slide` `range` and `act_hand` `ctrlrange` — the simulated hand could be
  commanded 10.25 mm past where the real one stops. That is the *second* place that
  correction failed to reach (the first, `mujoco_plant.py`'s hardcoded `355.0`, was
  found on 2026-08-21 in `2026-08-21-hand-continuity-remediation-and-archival.md`).
  Retiring the generator would have made "the XML is stale" permanent instead of
  detectable.
- **Retiring it does not close the class.** A frozen XML with no generator still has
  no test tying it to `hardware_config.yaml`. The failure mode would just change
  shape from "regenerating destroys the model" to "the model disagrees with the
  config and nothing says so".

So the direction is the one CLAUDE.md's contract pattern prescribes: a normative
statement (the header in the emitted file, plus the module docstring), a single
canonical enforcement point (`render_xml` — the one rendering entry point that both
`main()` and the gate call), and a test that fails when the invariant breaks.

### Why the gate drives `main()` instead of re-rendering its own copy

`test_committed_model_matches_generator` monkeypatches `OUTPUT_PATH` into `tmp_path`
and calls `main()`. The tempting alternative — assemble the expected text inside the
test — makes the gate test *its own* renderer, so a formatting change in `main()`
(the declaration, the header, the trailing newline) would pass the gate while
producing a file the generator no longer reproduces. That is a gate that is green
precisely when it should be red. Hence `render_xml()`: one function, called by both.

### Why the ball-mass disagreement was NOT reconciled

`throw_envelope.BALL_MASS_KG` derives a ball mass of **0.0952 kg** from the identity
`INERTIA_RATIO = m_hand/(m_hand + m_ball)` with `INERTIA_RATIO = 0.747` and
`m_hand = 0.281 kg`. It feeds `J_ASCENT_KGM2`, and through it the `ACCEL_AUTHORITY`
bound on the throw envelope. The physical ball is **0.071 kg**. They disagree by
+34 %; 0.071 kg would imply `INERTIA_RATIO = 0.798`.

Left alone, deliberately. `INERTIA_RATIO` is a tuned, hardware-validated
throw-shaping constant baked into Teensy firmware (`Trajectory.h`) and cross-checked
by four test files; it is not a measurement of the ball, and "reconciling" it means
retuning the throw, on hardware, with a firmware flash. Changing a control constant
as a side effect of a sim-codegen cleanup is exactly the kind of drive-by the
project's control-implications rule exists to stop.

What *was* done is make the collision impossible to walk into: the config keys are
`juggling_ball_mass_kg` / `juggling_ball_radius_mm`, **not** `ball_mass_kg`, so the
generated symbol is `hw.JUGGLING_BALL_MASS_KG` and can never be mistaken for
`throw_envelope.BALL_MASS_KG`. Two module-level constants with the same name and a
34 % gap, in a repo where one of them bounds a throw, is a trap. The YAML comment
states both values and why they differ.

## Changes

- **`config/hardware_config.yaml`** — `physics.juggling_ball_mass_kg: 0.071` and
  `physics.juggling_ball_radius_mm: 35.0` (owner-stated 2026-08-21: 71 g, 70 mm
  diameter), with the `throw_envelope` disagreement documented in place.
  Regenerated: two new constants in `hardware_config.{py,h}` and the five delivered
  copies. `Physics::JUGGLING_BALL_*` is inert in firmware — emitted because every
  section is emitted uniformly, the same as `HandEnv::`.
- **`sim/model/generate_mjcf.py`** — reads the ball spec from config; emits both
  balls from a `ball_specs` list that also drives the keyframe `qpos` and the
  sensors (so `nq` can never fall out of step with the bodies); emits `ball2_mat`,
  the `<contact><exclude>` and the two renderer-perf XML comments; adds
  `render_xml()` and `GENERATED_HEADER`; `OUTPUT_PATH` hoisted to module level so
  the gate can redirect it. The 2026-08-21 "regenerating destroys capability"
  banner is replaced — it is now false — with a statement that this file is the
  source of truth and why the drift gate exists.
- **`sim/model/jugglebot.xml`** — regenerated. Net diff: the 6-line generated-file
  header, plus the intended `0.355000 → 0.344750` on `hand_slide` `range` and
  `act_hand` `ctrlrange`. Nothing else moved.
- **`tests/sim/test_mjcf_drift.py`** — 6 tests: the render runs; the committed file
  is exactly what `main()` writes; the comparison is non-vacuous; the header is
  present; the two-ball tokens are all emitted; the ball spec still flows from the
  YAML (rendered against a sentinel config). The real comparison and its
  self-check call one `_assert_matches()`, so a green self-check proves the
  *actual* guard bites rather than a restatement of it that could itself drift.
- **The `<contact>` excludes are emitted per pair** (`itertools.combinations` over
  `ball_specs`) rather than as the hardcoded `(ball, ball2)`. Byte-identical output
  for two balls, and it keeps the "appending an entry is all a 3-ball model needs"
  comment true — a hardcoded pair would have left `ball3` colliding with both
  siblings, the same half-applied edit this gate exists to catch. Verified by
  rendering a 3-ball variant: 3 excludes, `nq = 47`, model loads.

### A third place the 2026-08-18 hand-stroke correction never reached

Regenerating turned `tests/sim/test_hand.py::TestHandModel::test_hand_slide_joint`
red: it asserted `jnt_range[hand_slide][1] == approx(0.355, abs=1e-4)` — the value
`jugglebot_geometry.hand_stroke_mm` left behind on 2026-08-18. So the correction
had missed **three** sim-side consumers, not two: `mujoco_plant.py`'s clip bound
(found 2026-08-21), the MJCF itself (this entry), and this assertion.

Fixed at the root rather than by swapping one literal for another — it now reads
`hw.GEOM_HAND_STROKE_MM / 1000.0`, so the next stroke change cannot leave it
behind, and its failure message points at the generator. The docstring records
that it is deliberately *not* `teensy_trajectory.hand_stroke_m` (0.355), the
throw-profile basis, which is a different number on purpose.

The parenthetical in `sim/plant/mujoco_plant.py` that said the XML "still carries a
0.355 m joint range because it has not been regenerated" was made false by this
change and is updated in the same commit.

Deliberately **not** touched: `sim/test_hand_stroke.py`'s `stroke_mm = 355.0` (a
manual viewer script, not collected; the plant clips it) and the `SLIDER_STROKE_MM
= 355.0` in three `tools/probes/` scripts. Neither is on the physical-travel path
this correction governs, and both predate it.

## Verification

Before adding the header, the generator was rendered to a scratch file and diffed
against the committed XML: **the only two differing lines were the intended
`hand_slide` / `act_hand` hand-stroke fix.** Nothing else in 221 lines.

The regenerated model loads in MuJoCo: `nq = 40`, `nbody = 17`, `ball` and `ball2`
both present at radius 0.035 / mass 0.071, `nexclude = 1`, keyframe `qpos` length 40,
`hand_slide` range `[0, 0.34475]`.

The gate was proven to bite, not merely to pass — three mutations applied to the
committed XML, each restored afterwards (sha256 confirmed identical to
pre-mutation):

| Mutation | Result |
|---|---|
| revert `hand_slide` range to `0.355000` | RED, naming line 79 and both values |
| delete the `ball2` body (the five-month failure) | RED, naming line 169 |
| strip the `GENERATED FILE` header | RED, 2 tests |

Full tier (`./run_tests.sh --full`, run 2026-08-21): **PASS — parallel phase
5734 passed / 3 xfailed / 0 failed in 489.91 s, serial phase 9 passed in 41.50 s,
537 s total.** Collection is +6 against `HEAD` (5746 vs 5740) — exactly this
entry's new test file, nothing removed. Re-run immediately before the commit
on the final tree: **same counts, 500 s + 45 s = 545 s.**

The first `--full` run of the session went RED on
`tests/sim/test_hand.py::TestHandModel::test_hand_slide_joint`, which is the
third-stale-site finding above; the run quoted here is after that fix.

## Open Questions

- **`INERTIA_RATIO` vs the physical ball mass.** 0.747 back-solves to a 95.2 g ball;
  the ball is 71 g. Either the ratio absorbs something else (seated-ball coupling,
  cup mass, a fudge from the original tuning) or the throw envelope carries a ball
  that does not exist. Quantified, it errs **safe**: `J_ASCENT_KGM2` is
  **1.291e-5 kg·m² against 1.230e-5** for the physical ball — 5.0 % *larger*, so
  `ACCEL_AUTHORITY_RPS2` (3261.5) comes out 5 % *smaller* than the real ball
  would allow. Conservative, and it does not bind anyway (`DECEL_FF_HEADROOM`
  binds first). Not urgent — but it is an unexplained 34 % in a constant that
  shapes every throw. (An earlier draft of this entry said "~2 % optimistic";
  that was wrong in both magnitude and sign, and is why the number is computed
  here rather than estimated.)
- **`../BallButler`'s delivered `hardware_config.h` was already stale** before this
  session (it still carried `HAND_STROKE_MM = 355.0f` from before 2026-08-18).
  Running `config/generate_config.py` here updated it, as designed; that external
  checkout now has an uncommitted, correct change that someone should commit on its
  own branch.
