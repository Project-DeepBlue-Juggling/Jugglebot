This document is the **definition-of-done for "the legacy `can_node` foundation is fully and robustly ported."** It enumerates every capability the retired Jetson `can_node` provided, maps each to its can-bridge (Teensy 4.1 firmware + `teensy_bridge_node.py` UDP bridge) equivalent, and classifies it **ported+validated / ported+unvalidated / PARTIAL / GAP**, with the concrete implementation differences. It is the prerequisite gate for any later MPC re-architecture (the replanner rides the same Teensy leg-command substrate either way).

It is a **living** doc: as a `ported+unvalidated` item is exercised on hardware it flips to `ported+validated` (cite the logbook/CSV); as a GAP is closed it flips to `ported+…`. Edit the row and the status counts when that happens.

## How this audit was produced

Nine capability domains were each mapped by an independent reader against `can_node.py` (1725 lines), `teensy_bridge_node.py` (1917 lines), the firmware (`ros_ws/src/jugglebot/Teensy_code_canbridge/`), and the `controller/teensy_link/` host observers, then **adversarially re-verified** by a second independent reader (refute-the-mapping pass). A completeness pass cross-checked the matrix against `can_node`'s raw interface inventory. Citations are `file:line`; statuses claiming `ported+validated` quote concrete evidence (a logbook hardware result, a passing test, or a CSV).

**Two domains' adversarial-verify pass and the completeness pass were interrupted by a session usage limit.** For those two domains (`telemetry-state-pubs`, `levelling-tilt-persist-timesync`) the high-severity claims were **independently re-confirmed by direct grep/read** during synthesis (2026-06-27): the production launch runs `orchestrator_node` *and* `teensy_bridge_node` together; `firmware_validated`/`is_homed`/`encoder_search_complete`/`levelling_complete`/`pose_offset_rad` are hardcoded in `teensy_bridge_node.py:682,696-702`; the firmware `encode_get_version` is defined but never called; the orchestrator/state-machine consumers exist as cited. Lower-severity rows in those two domains are **map-only** (so marked).

## The headline finding — automated orchestrator cold-start is broken against the bridge

Multiple independent gaps converge on one structural conclusion. The production `jugglebot_launch.py` launches **both** `orchestrator_node` (line 208) and `teensy_bridge_node` (line 216). The orchestrator state machine drives cold-start through interfaces the bridge **does not provide or always reports negative**:

| Orchestrator/state-machine dependency | What the bridge does | Effect |
|---|---|---|
| `BootHandler`: `if not ctx.firmware_validated` (`state_machine.py:232`) | publishes `firmware_validated=False` **unconditionally** (`teensy_bridge_node.py:682`); firmware `encode_get_version` **never called** | BOOT never advances → FAULT after `BOOT_TIMEOUT_S` |
| `HomingHandler` → `ActionClient(HomeMotors, 'home_motors')` (`orchestrator_node.py:61`) | serves only a `Trigger` service named **`home`** (no `home_motors` action) | `server_is_ready()==False` → homing request fails → FAULT |
| skip-if-already `is_homed`/`encoder_search_complete` (`state_machine.py:239,252`) | both hardcoded **False** (`teensy_bridge_node.py:696-697`) | skip-ahead never fires; no cross-session homed-state |
| `LevellingHandler` → `get_platform_tilt` client (`orchestrator_node.py:58`) | **no such service** | levelling faults |
| activate via `ActivateOrDeactivate 'activate_or_deactivate'` client (`orchestrator_node.py:52`) | serves split `activate`/`deactivate`/`configure` **Trigger** services; never rewired | automated activate cannot reach the bridge |
| `set_level_state` publisher (`orchestrator_node.py:77`) | **no subscriber** | gravity-offset persist silently discarded |

> **RESOLVED (2026-07-02, canbridge-foundation-coldstart-parity Phases 2/3/4/5).** Every row above is now closed: `firmware_validated` (Phase 3) + `is_homed`/`encoder_search_complete` (Phase 2/3) source from the relay/handshake; the hand surface + hand homing land in Phase 5; and **Phase 4** registers the `home_motors` action, the `activate_or_deactivate` / `get_platform_tilt` services, and the `set_level_state` subscriber on the bridge — with **zero edits** to `orchestrator_node`/`state_machine`. The orchestrator drives automated cold-start end-to-end; a runtime drift-guard test (`tests/ros/test_orchestrator_conduit_contract.py`) pins the bridge's served `(name, type)` set to the orchestrator's declared clients. See the per-row `CLOSED Phase N` markers. **Powered orchestrator-driven sitting PASSED 2026-07-02** — BOOT→HOMING(legs+hand)→IDLE fully automatic (`is_homed`/`fw_validated`/`enc_search`→1, no `control_mode='ERROR'`) + a 3× levelling cycle (`activate_or_deactivate` raise/lower, `get_platform_tilt` read [0.008,0.002] rad, `set_level_state` persist) — the 9 Phase-4 rows are now ported+validated.

**Why U1–U5 still validated cold-start:** the entire bring-up (encoder-search → home → configure → activate → deactivate, all six legs, 2026-06-23→27) was **operator-driven via direct `ros2 service call` to the bridge**, which bypasses the orchestrator state machine. So the *manual* cold-start foundation is solid and hardware-proven; the *automated* orchestrator path is not wired to the bridge at all. For a replanner / any autonomous cold-start this is a **prerequisite to resolve** — either retire the orchestrator state machine or rewire + re-expose the six missing/negative signals.

**Open operational question (needs a runtime check, not a desk read):** whether the wedged orchestrator (stuck BOOT→FAULT) actively interferes with operator-driven operation today — e.g. by publishing `control_mode='ERROR'`, which `motion_bridge_node` turns into an ESTOP — or is effectively dormant during manual cutover. Verify with a dedicated rclpy subscriber probe on `/control_mode` + the orchestrator state (NOT `ros2 topic echo`, which is flaky for high-rate RELIABLE topics on this Foxy box).

## What is solid (the reassuring half)

The **safety-critical fault behaviours are faithfully ported and, where the incident demanded it, carry explicit invariant comments and equivalence tests:**

- **CAN-loss deferred-stow safety inversion** (`logbook/2026-05-19`): preserved *exactly* in `fault_machine.cpp:160-208` (header enumerates the 5 invariants) — arm at detection, never command a dead bus, profiled stow only on confirmed reconnect, re-arm on mid-descent re-drop. Hardware-validated on a single bench leg (`logbook/2026-06-24` sub-test B: descent 0.30→0.006 rev, peak 2.472 ≤ 2.5 rev/s cap).
- **Soft-reset attempt limiter** (the bounce-loop incident): `MAX_SOFT_RESET_ATTEMPTS=1`, reset-does-not-refill-budget guard, dead-bus-budget-preservation — ported verbatim with the explicit "do NOT simplify" comment (`fault_machine.cpp:18-20,124-146`) and a passing executable-spec test.
- **Undervoltage gating + uniform-UV-benign distinction**, **homing hardstop arithmetic** (guarded by a 1:1 cross-check test `test_homing_xref.py`), **leg CAN encoding** (`'<fhh'`, scales codegen-identical), and the **`JB_OP_MAX_POSITION_STEP_REV` step gate** (re-expressed as a SetpointPump per-step gate + a firmware MAX_DEVIATION E-STOP).
- A **NEW** UDP-link (Jetson↔Teensy) watchdog that autonomously holds the legs on link loss — a failure surface that did not exist when the Jetson owned CAN (HW-validated, `logbook/2026-06-24` sub-test A).

> **On "GAP" and the hand (operator correction, 2026-06-27):** the hand has
> **always** been controlled by the Platform Teensy (it predates the can-bridge);
> `can_node`'s job was to be the **Jetson→CAN conduit** that forwarded hand
> commands onto the bus — directly to the hand ODrive (axis 6: `set_state`,
> `set_pos_gain`/`set_vel_gains`) and to the Platform Teensy (CAN id `0x6D0`
> `PLATFORM_TRAJ_CMD`: `set_hand_traj_cmd`, `smooth_move_hand`). The can-bridge
> now **owns that same CAN3 bus** (both the hand ODrive and the Platform Teensy
> sit on it), so it **must replicate `can_node`'s conduit**. It currently does
> not (rejects `HAND_AXIS` at `rpc.cpp:85-86`; no `0x6D0` forwarding) — so the
> hand command GAPs below are **real porting regressions, not off-scope items**.
> The `rpc.cpp` comment "platform Teensy owns the hand" conflates *"the Platform
> Teensy is the hand's real-time controller"* (true) with *"the can-bridge
> needn't relay Jetson hand commands"* (false). The hand must be processed the
> same way it was in `can_node`.
>
> Genuinely cross-Teensy (verify in a *platform-Teensy* audit, not necessarily
> defects of this migration): the **inclinometer** and **persisted home/level
> state** that physically live on the Platform Teensy.
