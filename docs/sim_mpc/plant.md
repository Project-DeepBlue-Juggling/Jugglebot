# Plant Interface

This page describes the MuJoCo simulation plant — how it models the Stewart platform, the coordinate conventions it uses, and how it connects to the MPC controller.

**Source files:**

- `sim/plant/interface.py` — `PlantInterface` ABC and `PlantState` dataclass
- `sim/plant/mujoco_plant.py` — `MuJoCoPlant` implementation
- `sim/model/jugglebot.xml` — MJCF model definition
- `sim/model/generate_mjcf.py` — Model generator (from Stewart geometry)
- `sim/ball/manager.py` — Ball physics and capture detection

## PlantInterface

The abstract interface defines four operations:

```python
class PlantInterface(ABC):
    def command(self, leg_extensions_mm: np.ndarray) -> None: ...
    def get_state(self) -> PlantState: ...
    def step(self, dt: float) -> None: ...
    def reset(self, pose_6dof: np.ndarray | None = None) -> None: ...
```

This abstraction exists so a future `HardwarePlant` can drive the real robot with the same MPC controller.

## PlantState

A frozen snapshot of the plant at one instant:

| Field | Shape | Units | Convention |
|---|---|---|---|
| `leg_extensions_mm` | (6,) | mm | Home-relative: 0 = home, positive = extended |
| `leg_velocities_mmps` | (6,) | mm/s | Positive = extending |
| `platform_pos_mm` | (3,) | mm | Offset from home center `[0, 0, init_height]` |
| `platform_rot` | (3,) | rad | Rotation vector (axis × angle) |
| `platform_twist` | (6,) | mm/s, rad/s | `[vx, vy, vz, wx, wy, wz]` |
| `time` | scalar | s | MuJoCo simulation time |
| `hand_pos_mm` | scalar or None | mm | Hand position from bottom of travel |
| `hand_vel_mmps` | scalar or None | mm/s | Hand velocity |

Hand fields are `None` when the model has no hand actuator (backward-compatible with hand-less models).

## Coordinate Conventions

### Extension Reference Frames

There are three related extension conventions in the system:

| Convention | Zero point | Used by |
|---|---|---|
| **MuJoCo slide** | Home position (geometric neutral) | Internal to MuJoCoPlant |
| **IK convention** | `init_leg_lengths_mm` (excludes ball joint offset) | StewartGeometry IK |
| **Home-relative** | Home position (slide = 0) | Public interface, MPC |

The conversions:

```
home_relative = ik_extension - home_extensions_mm
slide_m = (ik_extension + init_leg_lengths_mm - geom_home_lengths_mm × 1000) / 1000
```

Where `home_extensions_mm` is the IK extension at MuJoCo home (slide = 0), typically ~27-30 mm. This offset exists because the IK model measures from `init_leg_lengths_mm` (which excludes ball joint offset), not from the geometric home length.

### Platform Pose Convention

The platform pose is expressed as an **offset from the active pose**:

- **Position** `[x, y, z]`: displacement in mm from the active pose center. At the active pose, `pos = [0, 0, 0]` and the absolute platform height is `init_height_mm` (574.3 mm).
- **Orientation** `[rx, ry, rz]`: rotation vector in radians. At the active pose, `rot = [0, 0, 0]`.

This matches the production motion planner convention and keeps the MPC's decision variables centered near zero for better numerical conditioning.

### Sensor Extraction

Platform state is read from MuJoCo sensors (not directly from `qpos`/`qvel`):

| Sensor | MuJoCo Name | Conversion |
|---|---|---|
| Leg position | `slide_pos_0..5` | m → IK extension → home-relative (mm) |
| Leg velocity | `slide_vel_0..5` | m/s → mm/s (× 1000) |
| Platform position | `platform_pos` | m → offset from stow pose (mm) |
| Platform orientation | `platform_quat` | wxyz quat → rotation matrix → rotation vector |
| Platform linear velocity | `platform_linvel` | m/s → mm/s |
| Platform angular velocity | `platform_angvel` | rad/s (no conversion) |
| Hand position | `hand_slide_pos` | m → mm |
| Hand velocity | `hand_slide_vel` | m/s → mm/s |

## Command Pipeline

When the MPC calls `plant.command(leg_extensions_mm)`:

1. **Clamp:** Extensions are clamped to `[margin, stroke - margin]` to prevent actuator overshoot at mechanical stops. Default margin is 0 mm (MPC handles its own margin in `stroke_margin_mm`).

2. **Offset:** Home-relative → IK-convention: `ik_ext = ext + home_extensions_mm`.

3. **Scale:** IK extension (mm) → MuJoCo slide (m): `slide = (ik_ext + init_len - home_len × 1000) / 1000`.

4. **Actuate:** `data.ctrl[:6] = slide_m`. MuJoCo's position actuators drive the slide joints.

## MuJoCo Model

The MJCF model (`sim/model/jugglebot.xml`) is generated by `generate_mjcf.py` from the `StewartGeometry` class. It defines:

- **6 legs:** Each leg is a slide joint between a base attachment point and a platform attachment point, with a position actuator.
- **Platform body:** A single rigid body with the platform mass and inertia properties.
- **Hand actuator:** A slide joint on the platform for the linear throw/catch axis (optional).
- **Ball body:** A free-joint sphere for ball physics and capture detection (optional).
- **Sensors:** Position and velocity sensors on every joint, plus platform framequat and framelinvel.

### Actuator Model

MuJoCo's position actuators implement a PD controller internally. The gains are set to produce behavior approximating the first-order lag model the MPC assumes (τ = 30 ms). This creates a realistic coupling: commanded extensions don't appear instantly; they track through a dynamic response.

## Hand Control

The hand is an independent linear actuator on the platform. It is not controlled by the MPC — instead, it follows trajectories from the hand coordinator:

| Method | Action |
|---|---|
| `command_hand(pos_mm)` | Set hand to absolute position (clamped to stroke) |
| `hand_to_home()` | Bottom of travel (0 mm) |
| `hand_to_prime()` | Catch-ready position (~323 mm) |

Hand trajectories (`HandCatchSequence`, `HandThrowSequence`) are ported from the Teensy firmware's `Trajectory.h` and generate position commands sampled at the control rate.

## Ball Management

The `BallManager` handles:

- **Spawning:** Teleport ball to position, set velocity, enable physics.
- **Flight:** Standard MuJoCo rigid body simulation under gravity.
- **Capture detection:** Each physics substep, the ball manager checks MuJoCo's contact list for ball-hand geom pairs. When the contact solver reports a collision between the ball geom and any hand collision geom, the ball transitions to kinematic hold. Capture is latched — polled by the control loop via `check_and_capture()`.
- **Anti-re-capture:** After release, ball-hand collision is **disabled** (`contype=1`, ground-only) so the contact solver cannot trigger re-capture. The ball must reach 100 mm separation from the hand body before collision is re-enabled (`_must_exit_zone` flag). A 30-substep cooldown provides a secondary guard. This prevents immediate re-capture when the ball is thrown along the hand axis.
- **Kinematic hold:** After capture, the ball `qpos`/`qvel` are overwritten each substep to track the hand opening site exactly. No weld constraint or contact solver — purely kinematic.
- **Spawn in hand:** `spawn_in_hand()` places the ball at the hand opening site in kinematic hold with zero relative velocity. Used for throw sequences where the ball must be carried by the hand before release.
- **Release:** Ball is freed from kinematic hold with an optional ejection velocity (for throw sequences).

Capture detection runs at the physics substep rate (typically 2000 Hz with 0.5 ms timestep), not the 50 Hz control rate, to avoid missing fast-moving balls that pass through the hand between control steps. See [Hand & Ball Physics — Ball Capture Detection](hand_and_ball.md#ball-capture-detection) for full details.
