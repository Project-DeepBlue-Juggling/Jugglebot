# Jetson ↔ can-bridge Teensy — UDP protocol

> AUTO-GENERATED by `config/generate_udp_protocol.py` — **do not edit by hand**.
> Regenerate: `python config/generate_udp_protocol.py`

This is the single source of truth for the wire protocol between the Jetson
and the new can-bridge Teensy 4.1 (Phase 4 of `plans/active/teensy-can-offload.md`).

## Framing

Every datagram is one fixed-layout, typed frame. **No COBS** — UDP datagrams
already carry message boundaries, so stream-framing is redundant; a fixed
per-type layout is zero-allocation and deterministic-timing, which the hard
real-time firmware requires.

```
offset size field     type      notes
0      2    magic     u16 LE    0x4A42 ("JB")
2      1    version   u8        PROTOCOL_VERSION
3      1    msg_type  u8        MsgType
4      2    seq       u16 LE    per-(channel,direction) counter
6      2    length    u16 LE    payload byte count
8      N    payload   ...       type-specific (below)
8+N    2    crc16     u16 LE    CRC-16/CCITT-FALSE over bytes [0 .. 8+N-1]
```

CRC-16/CCITT-FALSE: poly `0x1021`, init `0xFFFF`, no input/output reflection,
no final XOR. Computed over the header and payload (everything before the CRC).

## Channels (UDP ports)

- **Port 5005 (STREAM)** — high-rate push: setpoint downlink, telemetry/
  diagnostic/profile/heartbeat uplink.
- **Port 5006 (RPC)** — request/response with retry-on-timeout: gain
  writes, state changes, encoder-search, SDO, homing, and the time-of-day query.

Static IPs: Teensy `192.168.42.2`, Jetson `192.168.42.1` (`/30` point-to-point).

## Messages

### Setpoint (`MsgType.SETPOINT`, J2T, STREAM port)

40 Hz MPC setpoint waypoints. Carries motor-rev-space quantities (Jugglebot convention: positive = leg extension) exactly as motor_guard's interpolator consumes them. The Jetson bridge does the same mm→rev / pose conversions motor_guard does today; the Teensy interpolator works purely in rev-space. `u1`/`u2` presence is signalled by the flags bits (NOT NaN sentinels).

Payload **156 bytes**. Python struct fmt: `<ffffffffffffffffffffffffffffffffffffIQ`.

| Field | Type | Count | Notes |
|-------|------|------:|-------|
| `u0` | f32 | 6 | Current motor positions (rev) |
| `u1` | f32 | 6 | Next waypoint (rev); valid iff flags bit0 |
| `u2` | f32 | 6 | Next-next waypoint (rev); valid iff flags bit1 — C1 continuity |
| `v0` | f32 | 6 | Forward-looking velocity from MPC (rev/s) |
| `accel` | f32 | 6 | Acceleration for Taylor extrapolation (rev/s^2) |
| `torque_ff` | f32 | 6 | Gravity+inertia feedforward (Nm) |
| `flags` | u32 | 1 | bit0: u1_present, bit1: u2_present |
| `t_origin_us` | u64 | 1 | Jetson-side wall-clock timestamp (us) |

### RpcRequest (`MsgType.RPC_REQUEST`, J2T, RPC port)

Generic RPC envelope. `method` selects the operation; `args` is a method-specific blob (see docs). `req_id` is echoed in the response for matching independent of the frame sequence counter.

Fixed head **8 bytes**, followed by a variable blob.

| Field | Type | Count | Notes |
|-------|------|------:|-------|
| `method` | u16 | 1 | RpcMethod enum |
| `req_id` | u16 | 1 | Caller-chosen id, echoed in response |
| `arg_len` | u16 | 1 | Bytes of args following the fixed head |
| `pad` | u16 | 1 | Alignment pad (zero) |

### RpcResponse (`MsgType.RPC_RESPONSE`, T2J, RPC port)
